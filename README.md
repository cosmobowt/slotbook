# Slotbook

Hosts publish when they are free, guests book a slot, and nobody is ever double-booked — even when the network, the clock or the user misbehaves.

**Stack:** TypeScript end to end · Fastify API · React (Vite) · PostgreSQL 16 · raw SQL through `pg` · Luxon for time zones · Vitest. No ORM, no starter template, no Redis.

## Run it

```bash
docker compose up --build
```

Then open http://localhost:3000. On boot the app runs migrations (behind an advisory lock), seeds a demo host and starts serving the API and the UI from one container.

- Demo host login: **demo / demo1234** (home zone Asia/Kolkata, Mon–Fri 09:00–13:00 and 14:00–17:00)
- Booking pages: http://localhost:3000/demo/intro-call (one-on-one, 30 min, 10 min buffer after) and http://localhost:3000/demo/group-workshop (capacity 5, 60 min)

Without Docker for the app (Postgres still from compose):

```bash
docker compose up -d db
pnpm i
DATABASE_URL=postgres://postgres:postgres@localhost:5432/slotbook pnpm --filter api dev   # API on :3000
pnpm --filter web dev                                                                     # UI on :5173
```

## Tests

```bash
docker compose up -d db && pnpm i && pnpm test     # or: docker compose run --rm test
```

All tests run against real Postgres (`slotbook_test` database, created by `docker/create-test-db.sql`). Override with `DATABASE_URL_TEST`.

| File | What it proves |
|---|---|
| `test/concurrency.test.ts` | 50 simultaneous holds over real HTTP: exactly 1 wins a one-on-one slot, exactly 3 win a capacity-3 session; 60 holds racing across a call and a workshop of the same host never produce an overlap. Each test re-checks the invariant directly in SQL. |
| `test/reliability.test.ts` | Idempotency-Key replay (sequential and 20 concurrent), key reuse rejected, idempotent confirm/cancel, hold expiry judged by the DB clock with the sweeper off, app clock skewed ±1 day changes nothing, buffers and off-grid times refused, reschedule in place. |
| `test/dst.test.ts` | Slot generation across the US DST change on 1 Nov 2026, the spring-forward gap, the fall-back overlap, date overrides, notice and horizon from the DB clock. |

## How double-booking is prevented

The application never decides whether a slot is free; Postgres does.

1. **Exclusion constraint** on `bookings` (`apps/api/migrations/001_init.sql`):
   `EXCLUDE USING gist (host_id WITH =, blocked WITH &&, session_id WITH <>) WHERE (status IN ('held','confirmed'))`.
   `blocked` is the booking plus its buffers as a half-open `tstzrange`. Two active bookings of a host may overlap only if they are seats in the same session. This holds across event types and across any number of API instances.
2. **Seat counting** for group sessions: each hold upserts and locks the `slot_sessions` row with `SELECT … FOR UPDATE`, counts active seats, then inserts. Without that lock, the capacity-3 test sold 6–11 seats in experiments; with it, exactly 3 every run.
3. **One clock.** Hold expiry is `now() + 5 min` and is checked as `hold_expires_at > now()` in SQL. Slot generation, minimum notice and horizon also use `SELECT now()`. The app server's and browser's clocks are never trusted. Because a constraint's `WHERE` cannot reference `now()`, each hold transaction first expires stale holds that overlap its range; a 30 s sweeper is housekeeping only.
4. **Idempotency.** `POST /api/holds` takes `Idempotency-Key`. The key is claimed in the same transaction as the hold (`INSERT … ON CONFLICT DO NOTHING`), so key and hold commit together or not at all; duplicates replay the stored response with `Idempotent-Replayed: true`; reusing a key for a different request is a 422. Confirm, cancel and reschedule are naturally idempotent.
5. **Outbox notifications.** `booking.confirmed / rescheduled / cancelled` rows are written in the same transaction as the change, so an event exists if and only if the change committed.
6. Deadlocks between two holds on overlapping sessions are possible by design of the locking; Postgres aborts one and `withTxRetry` reruns it, so the loser gets a clean 409.

## Time zones

Availability is wall-clock time in the host's IANA zone. Slots are generated by walking the host's local calendar dates and converting each window to instants for that date (never by adding 24 h to UTC). Steps within a window are absolute minutes, so a window spanning a DST change has its real length. The API returns UTC instants plus the same instant formatted in the guest's zone (`?tz=`); the browser only formats.

Policies, pinned by tests: a window starting in a spring-forward gap starts at the first real minute; an ambiguous fall-back time resolves to the earlier occurrence (like iCalendar — Luxon's own default is the later one).

Worked example (US DST ends Sun 1 Nov 2026), New York host at 09:00, guest in India: Fri 30 Oct → 13:00 UTC → 18:30 IST; Mon 2 Nov → 14:00 UTC → 19:30 IST.

## API

All bodies are JSON. Errors are `{ "error": { "code", "message" } }`.

| Method | Path | Notes |
|---|---|---|
| GET | `/api/hosts/{host}/events/{slug}/slots?from&to&tz` | `from`/`to`: ISO instant or `YYYY-MM-DD` in `tz`; default next horizon days. Returns `{ eventType, timezone, slots: [{ start, end, localDate, localTime, seatsLeft }] }` |
| POST | `/api/holds` | Header `Idempotency-Key` (8–200 chars, optional but recommended). Body `{ host, slug, start }`. 201 `{ holdId, start, end, expiresAt }`; 409 `SLOT_TAKEN`/`SLOT_FULL`; 422 `SLOT_INVALID`/`IDEMPOTENCY_KEY_REUSED` |
| POST | `/api/holds/{id}/confirm` | Body `{ name, email }`. 200 booking incl. `manageToken`; 410 `HOLD_EXPIRED` |
| GET | `/api/bookings/{token}` | View a booking via its private manage token |
| POST | `/api/bookings/{token}/reschedule` | Body `{ start }`. Moves the booking in place; same token |
| POST | `/api/bookings/{token}/cancel` | Body `{ reason? }` |
| POST | `/api/host/login` | `{ username, password }` → `{ token }` (Bearer) |
| GET/PATCH | `/api/host/me` | PATCH `{ timezone }` (validated IANA name) |
| GET/POST/PUT | `/api/host/event-types[/{id}]` | name, slug, durationMin 15–120, capacity, buffers 0–30, minNoticeMin, horizonDays |
| GET/PUT | `/api/host/availability` | `{ rules: [{ weekday 1–7, start, end }], overrides: [{ date, start|null, end|null }] }`, replaced atomically |
| GET | `/api/host/bookings` | Upcoming confirmed bookings |
| POST | `/api/host/bookings/{id}/cancel` | `{ reason }` |
| GET | `/api/host/notifications` | The notifications sink |
| GET | `/health` | Includes the database time |

## 60-second tour

1. Open `/demo/intro-call`. Slots appear in your browser's zone; switch zones with the dropdown and watch times move.
2. Pick a time. It is held for 5 minutes (the countdown is display only; the server decides).
3. Enter name and email, confirm, and copy the private manage link.
4. Open the manage link: reschedule to another time or cancel.
5. Open `/host`, log in as demo/demo1234: upcoming bookings (cancel with a reason), event types, availability editor (`Mon 09:00-13:00`, `2026-12-25 off`) and the notifications sink.
6. Try booking the same slot in two tabs: the second gets "That time is no longer available".

## Layout

```
apps/api/migrations/001_init.sql   schema and constraints (start here)
apps/api/src/engine/bookings.ts    hold, confirm, reschedule, cancel — all correctness paths
apps/api/src/engine/slots.ts       pure slot generation and DST policy
apps/api/src/engine/availability.ts slots endpoint
apps/api/src/routes/               HTTP layer (zod validation)
apps/api/test/                     tests against real Postgres
apps/web/src/                      React UI
```

## Optional extensions

None of the listed extensions is fully built. Time went into the reliability core and the tests that prove it. Partial: `/health` (reports DB time) and per-request IDs in Fastify's structured logs.

## Known gaps

- Notifications are recorded in the sink table; there is no dispatcher posting them to a webhook yet (`delivered_at` is reserved for it).
- No rate limiting or bot protection on public endpoints: one client can hold many slots for 5 minutes each.
- Host auth is a seeded username/password with bearer tokens in localStorage; fine for a demo, not for production.
- Changing a host's time zone or availability does not touch existing bookings (they are absolute instants, by design).
- Old `slot_sessions` and `idempotency_keys` rows are not pruned yet.
